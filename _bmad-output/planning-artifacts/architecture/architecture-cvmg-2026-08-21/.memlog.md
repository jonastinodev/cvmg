- (constraint) ville n'est pas une colonne SQL réelle sur cv — elle n'existe qu'à l'intérieur de donnees_json.personnel.ville (LONGTEXT), jamais remplie côté Express. Le cadrage du PRD (#9 : réutiliser ville ou colonne distincte) présuppose à tort que ville est déjà une colonne.
- (constraint) Convention déjà établie dans le code : tout champ qui doit être filtrable en SQL reçoit sa propre colonne dédiée sur cv (titre pour le métier, rayon_km, type, est_public), même si une copie existe aussi dans donnees_json pour le rendu. Rien d'équivalent à une table de correspondance (lookup table) n'existe ailleurs dans l'app — metiers.json lui-même est un fichier JSON plat lu à la requête, pas une table.
- (decision) Nouvelle colonne SQL dédiée 'zone' sur la table cv (option A), sans lien avec le champ 'ville' existant dans donnees_json — deux concepts de granularité différente (ville vs quartier), gardés séparés. Décision utilisateur, 2026-08-21.
- (decision) Le pilote couvre un seul quartier mais avec plusieurs sous-zones distinctes en son sein (confirmé utilisateur) -- élimine la correspondance par égalité simple. FR-1/FR-3 doivent calculer une vraie distance entre deux sous-zones nommées, pas comparer deux chaînes.
- (decision) [ADOPTED] La liste des sous-zones valides suit le même motif que metiers.json : fichier JSON plat listant les noms, lu à la requête -- pas de table de correspondance en base. Ratifie le précédent déjà établi par metiers.json pour une exigence structurellement identique (liste normalisée, pas de texte libre).
- (decision) Table SQL dédiée pour la distance entre sous-zones (zone_depart, zone_arrivee, distance_km) plutôt qu'un fichier JSON -- permet à FR-1 de combiner métier + zone/distance + rayon + seuil de densité (FR-8/FR-9) en une seule requête SQL, au lieu de fractionner la logique entre SQL et filtrage PHP. Décision utilisateur, 2026-08-21.
- (question) Le contenu réel des sous-zones et des distances (les noms, les valeurs en km) ne peut pas être rempli tant que la question #9 du PRD -- pardon, #1 -- (nom du quartier pilote) n'est pas tranchée. La spine fixe la forme de la solution, pas son contenu.
- (decision) Revue gate (3 lentilles) : structural seed corrige pour suivre le precedent existant (ajouter_*.sql), jamais editer creer_table_cv.sql -- confirme independamment par 2 revues sur 3.
- (decision) AD-4 ajoutee : integrite des noms de zone entre zones.json / cv.zone / zones_distances -- validation applicative a l'ecriture contre la liste canonique zones.json, collation utf8mb4_unicode_ci explicite sur les 3 surfaces. Corrige un trou trouve par la revue adversariale (JOIN qui echoue silencieusement sur un nom qui ne matche pas).
- (decision) AD-5 ajoutee : zones_distances stocke les deux sens explicitement (A-B et B-A) plus une ligne reflexive (zone, zone, 0) pour chaque zone -- matrice complete pour le quartier pilote. FR-1 fait un INNER JOIN simple, sans OR/LEAST/GREATEST. Promue depuis Deferred (reciprocite) suite a la revue rubric qui l'a jugee structurante, pas un detail d'implementation.
- (assumption) FR-17 retire des binds -- concerne le telephone, sans lien avec l'architecture de zone traitee par cette spine ; sa presence etait une derive de perimetre signalee par la revue rubric.
- (question) Ou vit la valeur du seuil de densite (FR-8/FR-9) reste explicitement differe -- le PRD (question #2, deja resolue) dit qu'aucune valeur n'est fixee avant simulation post-pilote ; cette spine fixe seulement qu'AD-1 (cv.zone) rend le comptage par zone possible, pas le mecanisme de stockage du seuil lui-meme.
